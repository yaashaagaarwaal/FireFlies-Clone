# Fireflies Clone — Meeting Notes & Transcription Platform

A Fireflies.ai-inspired meeting notes and transcription platform. Next.js/TypeScript frontend, FastAPI backend, SQLite database. AI summaries are generated by a zero-config heuristic by default, with a real Claude-backed generator that activates automatically if you set `ANTHROPIC_API_KEY` (see [Environment variables](#environment-variables)).

## Tech stack

- **Frontend**: Next.js 16 (App Router), TypeScript, Tailwind CSS
- **Backend**: FastAPI, SQLAlchemy 2.0, Pydantic v2
- **Database**: SQLite

## Architecture

```
Next.js frontend  --REST-->  FastAPI backend  -->  SQLite (fireflies.db)
```

- `frontend/lib/api.ts` — typed fetch client, single source of truth for API calls
- `frontend/lib/types.ts` — TypeScript types mirroring the backend Pydantic schemas
- `backend/app/models/` — SQLAlchemy ORM models
- `backend/app/schemas/` — Pydantic request/response schemas
- `backend/app/routers/` — thin HTTP layer: parse the request, call a service, return its result. No SQLAlchemy imports here.
- `backend/app/services/` — business rules and orchestration (existence checks, participant/assignee validation, full-replace semantics for PUT). Routes call services; services call repositories.
- `backend/app/repositories/` — data access only: queries and commits, no business rules. One module per aggregate (`meeting_repository`, `action_item_repository`, `participant_repository`, `user_repository`).
- `backend/app/services/ai_summary.py` — summary generation behind a `SummaryGenerator` interface: `HeuristicSummaryGenerator` (default, no external calls) or `LLMSummaryGenerator` (Claude, active when `ANTHROPIC_API_KEY` is set, with automatic fallback to the heuristic on any failure) — routers/schemas never know which one ran
- `backend/app/exceptions.py` — domain exceptions (`NotFoundError`, `InvalidInputError`) raised by services, translated to HTTP status codes by handlers in `main.py` — keeps the service/repository layers framework-agnostic

## Database schema

```
users                 id, name, email (unique), avatar_color, created_at

participants          id, name, email (unique, nullable), avatar_color

meetings               id, user_id FK→users, title, date, duration_seconds,
                       media_url, status, created_at, updated_at
                       CHECK duration_seconds >= 0
                       INDEX  date, title

meeting_participants   meeting_id FK→meetings (CASCADE), participant_id FK→participants (CASCADE)
                       composite PK (meeting_id, participant_id)      — M:N join table
                       INDEX  participant_id (reverse lookup)

transcript_segments    id, meeting_id FK→meetings (CASCADE),
                       speaker_id FK→participants (SET NULL, nullable),
                       start_time_sec, end_time_sec, text, order_index
                       CHECK end_time_sec >= start_time_sec
                       INDEX  (meeting_id, order_index)

summaries              id, meeting_id FK→meetings (CASCADE, UNIQUE — 1:1), overview_text

topics                 id, meeting_id FK→meetings (CASCADE), title, order_index,
                       start_time_sec (nullable — optional jump-to-chapter marker)
                       INDEX  (meeting_id, order_index)

action_items           id, meeting_id FK→meetings (CASCADE), text,
                       assignee_id FK→participants (SET NULL, nullable),
                       due_date (nullable), is_complete, created_at, updated_at
                       INDEX  meeting_id
```

All child tables (transcript_segments, summaries, topics, action_items, and the meeting_participants join rows) cascade-delete when their parent meeting is deleted. `SET NULL` foreign keys (transcript speaker, action item assignee) mean deleting a participant un-assigns their items instead of deleting meeting content. No real auth — a single seeded user stands in for the logged-in user, per the assignment's scope.

Schema is created via SQLAlchemy's `create_all()` (see `app/db.py: init_db()`), not a migrations tool like Alembic — appropriate for a from-scratch SQLite project at this scope; noted here as a deliberate simplification.

## API overview

```
GET    /api/health                                liveness + DB connectivity check

GET    /api/meetings          ?search=&participant=&date=&sort=recent|title
POST   /api/meetings                                optional transcript_text — parses + generates summary/topics
GET    /api/meetings/{id}                          full detail incl. transcript/summary/topics/action items
PUT    /api/meetings/{id}                           full replace
DELETE /api/meetings/{id}                           cascades to segments/summary/topics/action items

GET    /api/meetings/{id}/transcript                ordered by order_index
GET    /api/meetings/{id}/summary                   404 if not generated yet
GET    /api/meetings/{id}/topics                     ordered by order_index

GET    /api/meetings/{id}/action-items
POST   /api/meetings/{id}/action-items
PUT    /api/action-items/{id}                       full replace
DELETE /api/action-items/{id}

GET    /api/participants
```

`PUT` is a full replace, not a partial patch: `MeetingUpdate`/`ActionItemUpdate` require every core field, and omitting `participant_ids` on a meeting clears its participants rather than leaving them untouched — that's what "replace the whole resource" means.

Errors: a missing resource returns `404 {"detail": "..."}`; invalid-but-well-formed input (e.g. an `assignee_id` that doesn't exist) returns `400 {"detail": "..."}`; a body that fails Pydantic validation (blank title, negative duration) returns FastAPI's standard `422`; unhandled errors return `500 {"detail": "Internal server error"}` (logged server-side, detail hidden from the client). CORS is restricted to `CORS_ORIGINS` (defaults to `http://localhost:3000`). Interactive docs (Swagger UI) at `/docs`, raw OpenAPI schema at `/openapi.json` — both generated automatically from the routers/schemas above.

## Deployment

**Frontend → Vercel.** Zero-config for Next.js App Router, generous free tier. The app is entirely client-fetched (no Next.js API routes, no server component hits the DB directly), so there's nothing Vercel-specific to work around.

**Backend → Render** (Web Service, `render.yaml` at the repo root — import it as a [Blueprint](https://dashboard.render.com/blueprints)). FastAPI needs a long-running process, not a serverless function, so any FaaS target (Vercel/Netlify functions, AWS Lambda) is the wrong fit regardless of language.

**Is SQLite safe here? Only with a chosen tradeoff — this project currently runs the free/ephemeral option, deliberately, not by accident:**
- **Single instance, single worker, always.** SQLite uses file-level locking — multiple processes or horizontally-scaled instances writing to the same file will eventually hit `database is locked`. Never enable autoscaling or run uvicorn with `--workers > 1`, regardless of which option below you pick.
- **Persistent disks are a paid-only Render feature** (confirmed against Render's own docs) — free web services have an ephemeral filesystem, so any local file, including a SQLite DB, is wiped on every restart, redeploy, or ~15-minute idle spin-down. This is true of serverless/FaaS targets generally, not a Render-specific quirk.
- **Two real options, and this repo currently ships the first:**
  1. **Free, no card, data doesn't persist** (`render.yaml`'s current setting: `plan: free`, no disk). `scripts/start.sh` reseeds 5 fresh demo meetings on every boot, so the app is never stuck empty — but anything a user creates, edits, or deletes is gone the next time the free service restarts or wakes from idle. Free services also cold-start slowly (~30-50s) after spinning down. Fine for a demo/portfolio link; not fine for real use.
  2. **Paid, persistent** — Render's Starter plan (~$7/mo; verify current pricing at render.com/pricing) plus a ~$0.25/GB/mo disk (negligible at 1GB) is the cheapest tier that keeps data across restarts. Railway is a comparable-cost alternative. To switch: in `render.yaml`, change `plan: free` → `plan: starter`, add a `disk:` block (`name`, `mountPath: /var/data`, `sizeGB: 1`), and change `DATABASE_URL` to the *absolute* path inside that mount: `sqlite:////var/data/fireflies.db` (a relative path resolves against the ephemeral working directory even with a disk attached, silently defeating the whole point).

**Environment variables in production:**

| Platform | Variable | Value |
|---|---|---|
| Render | `DATABASE_URL` | `sqlite:///./fireflies.db` (set in `render.yaml`; see above for the persistent-disk alternative) |
| Render | `CORS_ORIGINS` | your Vercel production URL — set manually, not committed |
| Render | `ENVIRONMENT` | `production` (set in `render.yaml`) |
| Render | `ANTHROPIC_API_KEY` | optional, only for real LLM summaries — set manually if used |
| Vercel | `NEXT_PUBLIC_API_URL` | your Render backend URL |

**CORS.** Already environment-driven (`settings.cors_origins_list` in `main.py`) — no code change needed, just set `CORS_ORIGINS` to the real Vercel domain. Don't use `*`: `allow_credentials=True` is set, and browsers reject wildcard origins alongside credentialed requests.

**Production API URL.** `frontend/lib/api.ts` already reads `NEXT_PUBLIC_API_URL` with a `localhost:8001` fallback — no code change needed, just set the env var in Vercel.

**Health check.** `GET /api/health` already exists and checks real DB connectivity (`SELECT 1`), not just a static "ok" — wired into `render.yaml` as `healthCheckPath`.

**Seeding in production.** `backend/scripts/start.sh` seeds the database only if `fireflies.db` doesn't yet exist at `DATABASE_URL`'s path, then starts uvicorn. On the free plan (no disk) that file never survives a restart, so this check evaluates true — and reseeds fresh demo data — on every single boot; on a persistent disk it would instead mean "seed once, ever," skipping on every later restart. Either way `seed.py` itself always inserts with no existence check, by design for local dev — the guard belongs in the deploy script, not the seed script.

## Assumptions

- Single default user, no authentication (per assignment scope).
- Real speech-to-text, live-call bots, and third-party integrations are out of scope — placeholders only.
- AI summaries are generated by a zero-config heuristic service by default (no external calls). The same interface has a real `LLMSummaryGenerator` (Claude) that activates automatically when `ANTHROPIC_API_KEY` is set — see `backend/app/services/ai_summary.py` — with a safe fallback to the heuristic if the call ever fails, so meeting creation never depends on external-API reliability.
- `Participant` is a separate concept from `User`: a participant is anyone attendable/speakable in a meeting (including the app's own user, who also has a participant row so they can appear in transcripts). This mirrors how a real product separates "account" from "contact/attendee."
- Seeded data models realistic reuse: e.g. Priya Nair (engineering) attends 3 of the 5 seeded meetings as the same participant row, demonstrating the many-to-many relationship rather than duplicating her per meeting.
- Real meeting audio is out of scope. `frontend/public/sample-audio.wav` is a 20-second gentle placeholder tone generated locally (stdlib `wave` module — no network download, no copyright concerns), looped underneath a *logical* playback clock driven by the meeting's real `duration_seconds`. Seeking past the placeholder's own length wraps it (`time % audioFileLength`) rather than failing, so the UI stays correct for any meeting length while still producing genuine, audible HTML5 `<audio>` playback — not a faked timer.
- The API returns naive (no UTC offset) ISO 8601 datetime strings by convention — every one of them means UTC. All frontend parsing of those strings goes through a single `parseApiDate` helper (`frontend/lib/format.ts`) that explicitly treats them as UTC, because `new Date()` on an offset-less string is otherwise silently interpreted as the *browser's local time* — invisible on read-only display (the misread and the later re-localized formatting happen to cancel out) but a real, silent data-corrupting bug the moment a value round-trips through `toISOString()` on save. Found and fixed during manual testing of the edit-meeting flow.
- Transcript paste/upload accepts three auto-detected formats (see `backend/app/services/transcript_parser.py`): plain `[MM:SS] Speaker: text` lines (the prioritized path — continuation lines with no prefix fold into the previous turn), WebVTT (`.vtt`, sniffed by a leading `WEBVTT`), and JSON (`.json`, an array of `{speaker, start, end, text}` objects). File upload doesn't need a separate multipart endpoint — the frontend reads the selected file client-side via `FileReader` into the same textarea the paste path uses, so one `transcript_text` string field on `POST /api/meetings` covers both. Speakers are matched to participants by case-insensitive exact name; unmatched names become new `Participant` rows and are folded into the meeting's attendees, since the transcript is the ground truth for who actually spoke. Topics are mocked by picking evenly-spaced segments and titling each with a text snippet anchored to that segment's real timestamp, so they stay clickable/seekable. Action items are deliberately not auto-generated at creation — the assignment asks for those to be added afterward through the action-items UI.
